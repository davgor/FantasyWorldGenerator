# Portable contracts

- `blocks.json` is the block registry: every top-level key a generated world carries, with the schema that describes it or a stated reason it has none, its version binding, the module that writes it, whether it is carried across an age boundary and whether a legal world may omit it. It answers "what does a world contain", which was previously answerable only by reading a Python constant. It makes **absence representable** — `schemas/world-output.schema.json` has an open root, so a block that was never built, one that failed with `status: failed`, one switched off by an environment variable and one whose emitter broke this morning all validate alike. Measured at seed 42 size 17 and cross-checked against the size-33 sample: 65 rows, 9 blocks with a contract of their own, 49 carried across an age boundary, and **9 keys a world emits that no schema declares**. Drift fails in both directions, in `tests/test_block_registry.py` (no world needed) and in `tests/test_world_schema_conformance.py` (against a generated one); without those the file would be bureaucracy.
- `schemas/` contains export-only JSON envelopes for generated genesis data and the exhaustive potential-state asset list.
- `catalogues/world-assets.json` is a pinned semantic requirement input used to enumerate materials, vegetation, structures, effects, people roles, animation, and audio that supported generator states may require.
- `../Sim/icarus_sim/buildings.json` under `structure_blocks.common` is schema-1 design input for future city layouts for all civilizations: 80 non-housing requirements grouped into 11 blocks, with provisional dimensions, plot clearances, access and reuse candidates. It is not yet consumed by generation or the asset compiler. See [the measurement and layout contract](../docs/catalogue/human-civilization-blocks.md).

Several field names mean different things in different blocks — `tier` four ways, `status` at two depths across eight vocabularies, `camps` three ways — and a consumer joining two blocks on a name gets a plausible value and a wrong world with no error. [The consumer vocabulary](../docs/consumer-vocabulary.md) is the collision list and says which one you want; [030 Magnitude and identity conventions](../docs/decisions/030-magnitude-and-identity-conventions.md) is the convention that stops it growing, and rules out renaming any shipped field.

These files do not contain Unreal object paths or prove that game-owned assets exist. [Portable terrain taxonomy v1](terrain-taxonomy.md) defines recipe-3 school and terrain IDs (ML-01a). [Capabilities and coordinates v1](capabilities-and-coordinates.md) defines producer negotiation, axes, projections, units and independent coordinate fixtures (ML-01b).

[Kernel contracts v1](kernel-v1.md) completes the scoped ML-01c/d numeric, identity, failure and serialization boundary and defines ML-02's bounded accepted-counter proof. `schemas/counter-kernel.schema.json` supplies structural state/event/command/candidate/failure envelopes; the semantic oracle adds accounting, ordering and lexical integer checks. This is separate from existing generated-world schemas and seed behavior.


The current world envelope is schema **2**, recipe **3**, generation algorithm **16**, phase schema **2**, magic schema **4**, terrain schema **6**, and history schema **2**. Population profiles use schema **4** and building-pack inputs use schema **3**; settlements use schema **15** with the nested `city_layout` record at **2**, civilization reports use schema **2**, and rural reports use schema **9**. Age-transition wars move settlements, history and rural reports together: a city carries `war_history`, a ruin names the war that ended it, and `history.ages[].wars` lists them, so earlier worlds must be regenerated rather than advanced. Algorithm-8/9/10/11 worlds and retired generic human profile IDs require regeneration. Recipes 1/2 and old age/save contracts are rejected and must be regenerated. Natural IDs are sparse, never list offsets; retired IDs 9/10/11/12/14 are invalid. The 104 magical states use explicit `core.school` identities. Key locations use schema **1** with catalogue revision **1**; the block is additive and carries its own schema, so a consumer that does not read it is unaffected and a world generated without it replays identically. See [the canonical behavior contract](../docs/terrain-world-layers.md).

Every regeneration requirement on this page is an instance of one policy, and the policy is now written down: a generated world is disposable, and any generator change may invalidate every saved world, until the first player-facing release. See [023 World compatibility policy](../docs/decisions/023-world-compatibility-policy.md). The key-locations sentence above is the one compatible-change pattern this repository has found, and 023 names it as the shape to copy.

A world handed to a host is named by its content: `w_` followed by the first sixteen hex digits of sha256 over the transfer form, which is the export document with `build_stages` and `timing_ms` removed, serialised with sorted keys and no whitespace. One immutable version per name, and a host acting on one returns `schemas/operation-envelope.schema.json` rather than a world. See [026 World handles and the host store](../docs/decisions/026-world-handles-and-the-host-store.md) for what a host must guarantee and `../Fixtures/world-handle-v1.json` for the cross-host parity cases. Because a stored version outlives the generator that minted it, 023 is what a store enforces when it refuses a stale handle.

The exhaustive asset-list schema is **2**, scoped to recipe **3**. Production selectors use natural `biome_ids` or exact `biome_variant_ids`; catalogue schema **2** is synchronized across this directory, the packaged JSON and the readable production manifest. No current export includes the retired terrain surfaces.

Civilization identity, rules and appearance live in civilizations.json, which links the shared buildings.json libraries. See the [registry contract](../docs/civilizations.md). The former human-block catalogue path is a redirect notice.

Final-stage world exports may include `city_plans` version 8: local metre-scale rotated plots, canonical detailed elevation surfaces, terrain-routed streets, city fortifications, staffing, houses/apartments, ordered placement passes, housing-frontage reservation and explicit failures. `city_plans` is the only block that says which buildings a settlement has; `settlements.sites[].city_layout` is a node-scale district record and makes no placement claim. See [the city planner contract](../docs/city-planner.md) and [the settlement-records conformance record](../docs/conformance/settlement-records.md). Schema 2 of the world envelope remains compatible through this optional versioned section.

Final-stage exports may also include independent `hamlet_plans` version 3 and `castle_plans` version 3. Castle plans assemble fortification modules from fortress pins and do not share lifecycle with city packing. A castle plan declares no sleeping capacity: no structure in the castle registry carries a bed count, so castle plots carry no `beds` key rather than a zero beside a placed garrison, and `castle_plans.beds` says so. See [the castle planner contract](../docs/castle-planner.md) and [the hamlet planner contract](../docs/hamlet-planner.md).

Arctic registry schema 6/revision 11 requires independent crop temperature, founding minima, and economy winter fishing fractions. Population budget 4 exports a map of founding minima; founding report 4 records the same map. Old worlds require regeneration.

Resolved height tiles use `schemas/height-tile.schema.json` version 1. See [coordinates, shared samples and metre units](../docs/continuous-terrain.md).

Final-world `world_scene` version 1 carries globally located buildings, streets, regional routes and shared junctions. See [the unified globe contract](../docs/unified-world-scene.md).

See [unified globe diagnostics](../docs/unified-world-scene.md) for algorithm-16 sky suspension, college spacing, aridity, ley alignments and lab tables.

[Hero guild planning v1](../docs/hero-guild.md) is an opt-in Python planning capability with a separate versioned policy registry and result envelope. It does not change generated-world state or the counter kernel.

[Story web v1](../docs/story-web.md) is an opt-in block compiled from the `heroes` export by a separate package: per living hero the trope spokes, deterministic weights, the offered hook, three bound acts and exit threads. Schema `story-web.schema.json`; it changes no generated-world state and reads only exported blocks.

[NPC roster v1](../docs/npc-roster.md) is a block expanded from the placed staffing rosters by a separate package: one record per staffed post across `city_plans`, `hamlet_plans` and `castle_plans`, the cast folded in by `hero_uid`, a bounded `important` earmark for quest givers and an `alive`/`dead` birth state. Schema `npc-roster.schema.json`; it changes no generated-world state and reads only exported blocks.

[Villains v2](../docs/super-villains.md) is a core-emitted block, unlike the three above: the world model writes it during age transitions. Schema `villains.schema.json` describes everyone who ever held a region with a `living`/`fallen` status, the per-anchor tier ledger, the durable mark a fallen reign leaves, and the outlook report. Every container in it is closed, which is deliberate and unlike the rest of this folder: nothing sends this block, so the failure it has to catch is the emitter growing a field no contract mentions. Version 2 decays the tier ledger, which moves every world that has one. `key-locations` and `nomads` derive records from it.
