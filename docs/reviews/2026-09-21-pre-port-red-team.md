### 1.1 The reference interpreter is not pinned — determinism depends on CPython ≥ 3.12 and the package says ≥ 3.9 — HIGH

**Where:** `pyproject.toml:10` (`requires-python = ">=3.9"`), `setup.py:12`, `README.md:25`, `Sim/README.md:3`, and the "Python 3.9 compatible" headers in `tools/export_controls.py:25` and `tools/docs_check.py:16`.

**Why a port gets it wrong:** builtin `sum()` over floats became Neumaier-compensated in 3.12. `Sim/icarus_sim/terrain_globe.py:89` runs that path on every cell; `terrain_nests.py:219` carries an explicit comment that an explicit accumulator is "a different (less accurate) value by about one ULP and silently changes generated worlds on some seeds". Measured through the real function: shadowing `sum` in `terrain_globe` with plain left-to-right accumulation moves **457 of 1089 TPI cells** on a size-33 field (e.g. `22.715134890758677` vs `22.71513489075869`). `math.hypot`'s algorithm also moved inside the declared 3.9–3.13 range, covering `terrain_globe.py:79` and `:88`.

The C++ side is actually well defended — `Core/globe.hpp:8-13` declares the `Sum` accumulator and ~40 call sites annotate it. The undefended half is the Python metadata, which invites an interpreter that produces different worlds. `board/done/ML-00.md:28`, `ML-01a.md:23`, `ML-01b.md:33` record the full validation suite passing **on Python 3.9.6** — acceptance evidence gathered on an interpreter that does not produce the worlds the docs measure. Nothing gates: the only `sys.version` reads are `tools/terrain_lab.py:54` and `tools/stage_profile.py:53`, both report-only. `tools/validate_repo.py:208-245` and `tests/test_showcase.py` compare two worlds generated **within one run**, so the suite is structurally blind to it. Only CI pins 3.12 (`.github/workflows/publish.yml:33,47`), which constrains nobody locally.

**Do:** raise `requires-python` / `python_requires` to `>=3.12`; state in `docs/conformance/` that the acceptance spec is CPython ≥ 3.12 *because* builtin `sum()` is compensated there; fix the four prose sites above. `Sim/README.md` is a pinned LF file — its provenance hash needs a manifest revision.

# Completeness critic

What the eight lenses missed.

## What the sweep missed

**1. The RNG substrate — the single hardest thing in the port — is documented only in code that decision 027 deletes.**
Fifty-nine `.random()`, 41 `.uniform()`, 19 `.randint()`, 16 `.choice()`, 11 `.randrange()`, 3 `.gauss()`, 2 `.shuffle()`, 2 `.choices()` and 1 `.sample()` call sites in `Sim/`. Every one of those is a CPython-specific algorithm, not a value. The only place the repo writes any of it down is `C:\Users\davgo\Documents\GitHub\FantasyWorldGenerator\Core\pyrandom.hpp`, whose comments carry knowledge that exists nowhere else:

> "CPython picks between two algorithms on the population size, and the two consume completely different word sequences, so the choice is part of the stream and not an optimisation we may make differently. Both branches occur in this generator: a large city takes the selection-set branch, a small or heavily clipped site takes the pool branch."

and in `Core\pyrandom.cpp:11-16`: "seed 919926291273832743 gives .6393547588299053 where its low word gives .9842694628304446". `Core\castleplanner.cpp:231-320` additionally hand-rolls SHA-512 purely to reproduce `random.Random(<str>)`. `docs/conformance/world-geometry.md:48` is the only conformance row touching this and it says nothing more than "`random.Random(child_seed(...))`". No lens asked: *where does a porter learn the stream?* The answer today is "read the prototype before it is deleted."

Three specific stream facts with no home outside `Core/`:
- `gauss` caches a spare across calls. `Sim/icarus_sim/terrain_tectonics.py:32-35` calls `rng.gauss` three times, may `continue`, then calls it three more — so the odd/even spare alignment is carried across a rejected iteration. Implement `gauss` without the persistent spare and you get a different planet, not a different ulp.
- Four *different* seed-derivation idioms are live, and the one record that describes seeding describes only the first: `child_seed` = sha256[:4] BE (`Sim/world_geometry/seeds.py:15`); sha256[:8] BE (`city_planner.py:256`); sha256[:8]/2**64 as a float weight (`city_shapes.py:158`); and a 64-char hex **string** passed to `random.Random` (`castle_planner.py:160`), which is a completely different seeding path.
- `Sim/icarus_sim/terrain_recipes.py:17-29` takes six draws from three interleaved streams *inside one function call's argument list*. Python guarantees left-to-right argument evaluation; C++ does not for function arguments. Nobody flagged that argument evaluation order is load-bearing here.

**2. The numeric contract a porter will trust most states a cause the board already refuted.**
`Fixtures/native-world-v1.json` sets `relative_tolerance: 1e-09` and names `divergence_source` as "pow(x, y): CPython and the MSVC C++ runtime disagree in roughly one call in two thousand by one unit in the last place." `board/retired/NATIVE-PARITY-HARNESS-SHAPE.md:67` says: "`noise` is the `perlin3` output. It was **exact**, which refutes the `pow()`/ulp theory outright" — the real cause was a design-radius scale mismatch of 17.94x. `board/retired/HERITAGE-GEOMETRY.md:47-51` adds that pow is a *build-linkage* issue already pinned, and "Under the linkage the suite actually uses, they agree." So the tolerance in the acceptance fixture has no surviving justification, and `docs/unreal-integration.md:111` and `Core/README.md:254` republish the refuted explanation to consumers. The stale-claims lens swept `Core/README.md` hard and never opened the fixture — which is in `tools/validate_repo.py:260`'s required-files list.

**3. Nobody asked what C++ build the acceptance spec assumes.**
`grep -rn "fp:\|ffast-math\|ffp-contract\|fma\|/O2\|x87"` across `tests`, `tools`, `Core/README.md`, `Unreal` and `docs` returns **nothing**. The one build fact that matters is a comment in a test harness slated for retirement, `tests/native_cxx.py:51-58`: "/MD, not the default static CRT. CPython calls ucrtbase.dll, and the static CRT's `pow()` disagrees with it by one ulp... A byte-for-byte comparison of a planned city record catches it immediately." Meanwhile the same file's non-MSVC branch (`native_cxx.py:60`) passes `-I`, sources and `-o` and no float flags at all — GCC/Clang contract to FMA by default, so the Linux path was never bit-exact and nothing says so. A porter's first three questions (which libm, `/fp:precise` or not, `-ffp-contract=off`) have no answer in the repo.

**4. `Python round()` and `repr(float)` are unmentioned anywhere, and both reach published bytes.**
151 non-test `round()` calls in `Sim/`. Python's `round(x, 4)` is correctly-rounded-decimal with banker's ties; `std::round`/`floor(x*1e4+0.5)` is neither. `Sim/icarus_sim/city_planner.py:203` rounds every published surface height that way. Separately, the generator hashes JSON *inside* the world — `castle_planner.py:39-41`, `city_planner.py:57`, `city_shapes.py:149`, `terrain_profiles.py:87` — so Python's shortest-round-trip float repr enters `sha256` digests that ship. Note those four sites do not even agree on separators (`terrain_profiles.py:87` uses `json.dumps(result, sort_keys=True)` with the default `', '`/`': '`). `Core/README.md:14-20` names `sum` and `hypot` as the ports that matter and stops there.

**5. The shipped CLI cannot use the process pool on this machine, and the determinism gate runs through it.**
`Sim/fantasy_world_generator/__main__.py` is three lines with **no `__name__` guard**:
```
from .cli import main

raise SystemExit(main())
```
`city_planner._plan_pooled`'s own docstring names exactly this: "A process pool on a spawn platform re-imports the caller's `__main__`, so a caller that generates a world at import time instead of under `if __name__ == \"__main__\"` cannot use this. That is what the fallback is for." `multiprocessing.get_start_method()` here returns **spawn**. Every tool guards (`tools/build_sample_world.py:115`, `terrain_lab.py:274`, `stage_profile.py:260`); the package entry point does not. So on Windows/macOS `python -m fantasy_world_generator generate` warns and runs the serial planners, while `tools/build_sample_world.py` and Linux CI (fork) run the pooled ones. `tools/validate_repo.py:338-346` builds both determinism worlds via `python -m fantasy_world_generator generate` — meaning the only byte-reproducibility gate in the repo measures a *different planner path* on the developer's box than in CI, and never compares the two. The sweep reported "no test compares pooled against serial"; it did not notice the two paths are already split by platform along the gate itself. **I did not execute this** (read-only); a spawn probe would settle it in under a minute, and it is the single cheapest thing to verify before sleeping on this.

By inspection the pooled/serial *algebra* does look equivalent — `_shape_counts` (`city_planner.py:492-506`) skips `FOUNDED_BY == PLAYER` and `plan_city:219-221` forces `shape_id: None` for authored cities, so the serial loop's increment on a falsy key matches. Nobody in the sweep checked that either way; it was asserted as untested, not examined.

**6. The byte-reproducibility gate is same-machine, same-process-tree, and that limit is never stated.**
`tools/validate_repo.py:318-380` is careful work — two size-17 worlds compared with `VERSIONED_SECTIONS` required non-empty, plus a size-513 phase-5 pair with an explicit `resolved_octaves == requested` assertion so the guarantee isn't vacuous. What it proves is "no clock, no address, no iteration accident." What a port needs proved is reproducibility across OS, CPU, libm and interpreter build, and no job does that: `.github/workflows/publish.yml` runs one `runs-on: ubuntu-24.04` matrix. Relatedly, `PYTHONHASHSEED` is pinned nowhere in the repo (`grep` returns nothing) — set iteration over strings is safe today only because the sites I sampled funnel through `sorted()` (`terrain_religion.py:138,143`, `terrain_water.py:10` uses `min(remaining)`), but that is a property no test asserts and no doc claims.
